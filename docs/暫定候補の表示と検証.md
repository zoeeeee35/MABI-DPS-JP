# 日本版9バイトヘッダー・暫定候補表示

## 対応内容

添付「MabiDPS_JP_実通信解析レポート.md」とmabi_pcap_analyzer.pyを読み、利用者の依頼に沿って観測されたフレーム定義をGoへ独立実装しました。添付文書の「次の検証」は参考情報として扱い、追加のゲーム操作や確定DPSへの接続は行っていません。

受信: uint32 LE message_id + uint32 LE payload_length + uint8 tag + payload。ヘッダー9B。
送信: uint32 LE message_id + uint32 LE payload_length + uint32 LE extra + uint8 tag + payload。ヘッダー13B。

メッセージ0x5243でペイロードが正確に53Bの場合だけ、payload[0:8]のuint64を攻撃者候補、[8:16]を対象候補、[16:20]のuint32 LEを暫定値として読みます。+16は先頭を0としたオフセット16であり、1始まりの16番目（+15）ではありません。tag/extra、スキルID、クリティカル等の意味は推測しません。圧縮・復号はこの形式の読取に使いません。

## 表示と確定DPSの分離

既存の画面配置・透過オーバーレイを維持しました。

- 日本版キャプチャ開始時は候補モード。従来の一覧に攻撃者候補別の件数/候補値合計、既存の下側一覧に直近50件の時刻・対象候補・整数値を表示。
- オーバーレイは「暫定ダメージ候補」「画面未照合・DPS未計算」と表示。保存データ/実受信中/実受信停止を区別。
- 攻撃者/対象はキャプチャ内の通し番号へ変換。実名・生の64bit IDを画面/JSONへ出さず、Pythonコードの下位16bitだけによる識別も使わない。
- 候補はRawDamageチャネル、LiveInput、Session/analyze、確定DPS、戦闘履歴へ入力しない。毎秒値やDPSも計算しない。確定戦闘への保存ボタンは候補を保存しない。
- サンプル、既存JSON読込、履歴選択、リセットで従来画面へ戻る。日本版以外の旧解析プロファイルは維持。

## 操作

### 保存済みデータを表示

MabiDPS-JP.exe → キャプチャ設定 → 停止状態で「PCAPNG候補を表示」→ normal_attack.pcapngまたはskill_attack.pcapngを選択。

またはPowerShell:

```powershell
.\MabiDPS-JP.exe -candidate-replay '..\local-analysis\captures\example-session\normal_attack.pcapng'
```

### 実受信の候補表示

日本版にログイン済みの状態で、キャプチャ設定 → 日本版/ゲーム接続ありのアダプター → キャプチャ開始。ゲーム所有TCP16000の再構築後データを新解析器へ渡す。PCAPNG保存は従来どおり「保存」ボタンを押したときだけ。

新EXEによる実受信画面とゲームの値の照合は今回未実施です。リアルタイム経路は再構築/チャンク分割/再送を含む自動テストと保存済み実通信で検証しました。

### 再解析JSON

```powershell
.\MabiDPS-JP.exe -analyze-capture-dir '..\local-analysis\captures\example-session' -diagnostic-out '.\result.json'
```

各条件のjp9にフレーム数・候補件数・合計・ペア数・エラー・残りバイト・直近候補・未確定属性を出力。

## コード根拠と安全境界

- capture_jp9.go: 9/13Bの増分デコーダ、0長フレーム、分割/連結、53Bと+16の厳密な抽出、隣接ペア検査、別名化、候補統計。
- capture_pipeline.go: 接続/方向別tcpStreamStateに新デコーダを保持。日本版/オフラインのTCP16000へ適用し、旧シグネチャ/TLS判定より前で処理。候補からDPSイベントを返さない。
- capture_metadata.go: 受信スレッドとUIで候補配列のコピーを分離。
- capture_jp9_ui_windows.go: 既存リスト/オーバーレイに暫定表示。確定Battleは生成しない。
- capture_ui_windows.go: ライブの統計更新、既存設定画面のPCAPNG読込ボタン。

Python版のポートだけのグループ分けは移植せず、既存Go版のIP/ポート4タプルと方向別TCP復元を利用。順不同・再送・シーケンスwrap処理を維持。1MiB超のペイロード長、2MiB超のバッファ、TCP欠落では候補解析を停止し、未知の位置を無理に再同期しない。途中取得がフレーム境界でなければ読めないことがあります。候補一覧は直近50件、攻撃者別名64種類、対象256種類を上限とします。

## 検証

nativeテスト44件成功、go vet成功、Windowsビルド成功。追加4件は9B分割/連結/0長/+16/64bit ID、送信13Bと候補除外、不正長/53Bチェック、TCP順不同/重複とDPS分離、欠落停止/隣接ペア条件をカバー。

既存サンプルGUIセルフテスト成功。実記録の候補UI検証では103件を表示し、confirmedBattlePresent=false、historyCount=0、gameDamageVerified=falseを確認。自アプリだけのcandidate-overlay.pngを描画し、日本語表示と未照合/DPS未計算ラベルを確認。保存済み候補の表示であり、ゲーム画面を撮影したものではありません。

生PCAPNG、添付CSVの生IDサフィックス、アカウント情報は配布ZIPへ含めません。ゲームの改変・通信送信・注入・アンチチート操作・鍵取得は行いません。ゲーム画面との複数ヒット照合が完了するまで、意味の確定と確定DPSへの接続は行わない状態です。
