# 実受信機能の開発記録・技術的な到達点

2026-10-25。既存のMabiDPS-JPに追加した実験機能であり、別プロジェクトではない。作業ブランチは`feature/jp-passive-capture`。日本版の正確なダメージ取得の完成宣言ではない。

## 既存コードとの接続

`capture_windows.go`（Npcap受信）→ `capture_process_windows.go`（プロセス所有の接続照合）→ `capture_pipeline.go`（パケットとストリームの分離）→ `capture_tcp.go`（順序復元・再送除外）→ `capture_protocol.go`（既知の旧形式・Brotli）→ `capture_live.go`（仮名化・プレイヤー選択）→ `Session.recompute()` → `analyze()` → 既存Windows画面・オーバーレイ。

元の入力は`CombatLog.Players`と`CombatLog.Events`。実受信では到着時刻を基準とした相対ミリ秒と、一意なイベントIDを生成する。異なる接続から遅れて到着したイベントは、末尾の記録時刻より前にならないよう補正し、ゲームサーバーの時刻とは区別する。サンプル再生は従来の`Session.advance()`のまま残した。

## 公開コードで確認できたこと

対象: [teto-ri/Mobinogi_Meter](https://github.com/teto-ri/Mobinogi_Meter)、基点`eed9089bb4a24a69f8db349dbe4bd6eb9529362f`。

`Decomplie_new_base/mobi_capture.py`:

- 34行: TCP送信元ポート16000を固定する。
- 37〜38行: 開始`3A 04 00 00 00 00 00 00`、終了`04 00 00 00 00 00 00 00`を探す。
- 43〜47行: ダメージ1283、スキル1432等の種別を定義する。
- 270行付近: 攻撃者候補4バイト、未解釈4バイト、対象4バイト、未解釈4バイト、名前長、名前、ダメージ、未解釈12バイト、フラグ6バイト、スキルID4バイトを読む。
- 300行付近の`parse_data`: 種別・長さ・符号化種別を読み、符号化1ならBrotli展開する。暗号鍵取得・暗号復号の実装は見当たらない。圧縮展開と復号は別の処理である。
- `get_skill_for_damage`: 時刻とシーケンスの近さからIdleスキルの対応を推定する。本実装はこの推定を採用していない。
- `processor`: 1個の`buffer`と`expected_next_seq`を使い、順序不一致は警告しながら連結する。4タプルごとの分離・厳密な再送排除はないため、そのままでは混線・二重集計の問題がある。

明示ライセンスが確認できないため、このPythonコードはコピーしていない。公開された配置・数値という観察事実をもとに、境界検査を伴う別実装を作った。名前の文字コードは推定せず、名前のバイト列は長さに従いスキップする。

TCP再構築にはMITのMOGUGI `lib/packet/tcpReassembly.go`を流用し、取得用コールバックへ適合させた。出典はファイル先頭にも記載した。4MBの保留上限と3秒の欠落タイムアウト、再送の重複除外、順序復元を引き継いでいる。欠落後はフレーム途中の状態を捨て、欠落件数を記録する。

[参照元MabinogiTools/DamageMeter](https://github.com/pblyat/MabinogiTools/tree/main/DamageMeter)のREADMEは、パッチによってそのコードが動作しなくなったと明記している。旧公開コードが現在の日本版でそのまま動くと判断する根拠はない。

[Scouter Liteの公開更新履歴](https://scouter-lite.mobi/)にはRustパーサー、WinDivert、ゲーム更新後の解析修正の記載がある。しかし現在のフレーム・暗号・ID仕様は公開ページから分からない。インストーラーの逆コンパイルや独自アセットの流用はしていない。

## 取得方式の選択

Npcapを採用した。このPCには既にDLLとドライバーがあり、実機でのアダプター列挙とキャプチャ開始に成功した。新たなドライバーやサービスは導入していない。Npcap自体の再配布許諾は別途必要なため、DLL・ドライバー・インストーラーは同梱しない。[Npcap公式API](https://npcap.com/guide/wpcap/pcap.html)、[再配布条件](https://npcap.com/oem/redist)。

WinDivertにもSNIFF/RECV_ONLYによる受動観測の方式があるが、今回追加する必要はなかった。[公式説明](https://github.com/basil00/WinDivert/blob/master/doc/windivert.html)。送信・再注入・フィルターによるゲーム通信の遮断は実装していない。

- 非プロミスキャスモードで選択アダプターのTCP/UDPを取得する。UDPは待受所有情報との照合件数だけを数え、ゲーム用デコーダーへは渡さない。画面の「受信」は、このアダプターで取得したTCP/UDPの合計件数であり、ゲーム以外や両方向を含む。
- その後、`GetExtendedTcpTable`のIPv4/IPv6の接続情報と所有PIDを照合する。`PROCESS_QUERY_LIMITED_INFORMATION`で実行ファイルのベース名だけを確認する。メモリ読取・改ざん・注入用権限は要求しない。
- 送信元・送信先・ポートの4タプルが対象クライアント所有の受信方向と合致するデータだけを、アプリケーション形式のデコーダーへ渡す。他通信のペイロードはデコードしない。
- 接続情報は毎秒更新する。接続直後や切替直後の検出遅延による取りこぼしは未解決の検証事項。
- IP・ポート・元の攻撃者IDは診断ログに保存しない。元IDはセッションごとの秘密乱数でHMAC仮名化する。生パケットのファイル保存は実装していない。
- TLSレコードと整合する先頭を見つけたストリームはTLS形式接続として数え、復号や平文デコードを行わない。この判定だけでゲームの全接続がTLSと断定しない。

## 実機で確認した範囲

最初の観測は`live-observation.json`に保存した。日本版クライアント起動中、Realtekのアダプターで停止時点の取得TCP32,995、対象クライアント所有TCP2,411（ペイロードあり2,322）、対象接続7本、戦闘候補0件。TLS形式の接続は2本。TCP再構築の欠落・ドライバー欠落の診断値は0だった。

この結果は「Npcap→アダプター→対象プロセス所有TCPの識別・受信」を確認するもの。戦闘データがその接続に含まれること、ダメージが正確に読めたこと、暗号化の有無を証明するものではない。TLSの2本がログイン・Web API等なのか戦闘なのかも未確定。

実行サンドボックス内の診断では、TCP一覧取得がエラー5で制限され、ループバックだけが見えた。実際のWindowsアプリとして起動した検証では、物理アダプターと対象接続を取得できた。サンドボックス内の失敗をユーザーPC全体での失敗とは扱っていない。

## 27件の自動テストとGUI検証

従来の13テストを保持し、新たに14テストを追加した。`go test -tags native ./...`、`go vet -tags native ./...`、EXE生成、サンプルGUI再生テストが成功した。

追加した検証は、平文/Brotliの合成フレーム、1バイト分割、ペイロード中の区切り形状、TCP順序逆転・再送・複数接続分離、対象外通信の除外、TLS形式を復号しないこと、不正な長さ・未知符号化、明示的なパーティ選択、仮名化、ライブの無ダメージ終了、履歴重複キーの安定性、段階別診断、合成PCAPの再生、Ethernet→TCP→デコード→DPS→履歴の接続である。

合成PCAPで成功したことと、実ゲームのPCAPで成功したことは区別する。実ゲームの生PCAPは保存・提供されていない。新しい「旧形式の目印」の件数は固定パターンの一致数だけで、未知のバイト列や個人情報を記録しない。目印だけが一致しても戦闘イベントとして採用しない。

## 現在の障害と次に必要な確認

1. 攻撃操作と観測を同期し、画面の既知ダメージ1件が受信中に発生する条件で照合する。
2. 旧形式の開始・ダメージ・スキル目印を調べる。見つからない場合、UDP等の別経路、現在の外側フレーム、圧縮・暗号化の違いを区別する必要がある。戦闘デコーダーの入力はTCPのみ。UDPは所有待受との照合候補数を追加したが、実機でのUDP再観測と、UDPに戦闘が流れるかの確認は未実施。
3. 現行日本版の公開仕様、または認証情報を含めない適切に許可されたテストデータにより、境界・種別・データ型を確定する。暗号化されていれば、鍵の抽出・復号回避へ進まない。
4. 敵／プレイヤー／パーティの識別とスキルの意味を実画面と照合する。DPSに届くまでの技術経路があっても、この照合なしに正しい与ダメージとは主張しない。

## 利用規約上のリスク（技術可否と別）

受動キャプチャが技術的に可能でも、運営に承認されたという意味ではない。日本版の[運営ポリシー4-4](https://m.nexon.com/terms/1496)には非認可プログラムに関する制限がある。これは今回のデコード不成立の技術的原因ではなく、実利用についての別のリスクである。

## 攻撃テストの追加結果

ユーザー申告は最初の与ダメージが約730、攻撃5〜10回。該当テストの停止後の画面診断は、取得TCP28,630、ゲームTCP1,736（ペイロードあり1,501）、対象接続6本、戦闘候補0件、旧形式の開始・ダメージ・スキル目印は各0件。記録は`attack-observation.json`に残した。約730を正確な測定値とみなしたり、5〜10回を確定した命中数としてテスト期待値にしてはいない。

したがって、攻撃があったという申告は得たが、与ダメージとのデコード照合は成功していない。上記テストはUDP診断追加前のTCP取得ビルドで実施したものであり、UDP0件を確認したという意味ではない。

この結果を受け、WindowsのGetExtendedUdpTableによるIPv4/IPv6待受所有情報を追加し、対象クライアントが所有するUDP受信候補を数えるようにした。同一ポートを複数PIDで共有するものは保守的に除外する。UDP待受は相手側の接続情報を提供しないため、表示はあくまで「ゲーム所有候補」であり、戦闘通信と断定しない。UDPペイロードのデコード・ダメージ抽出は実装していない。

追加の2テストは、IPv4/IPv6・ワイルドカード待受の照合、対象外UDPの除外、UDP内に旧戦闘形式と同じバイトがあってもダメージへ採用しないこと、UDP候補の診断状態を検証する。これで計27テスト関数となった。実機UDP診断はまだ未検証であり、今回の攻撃でTCP/UDPのどちらに戦闘が載るかは未確定。
