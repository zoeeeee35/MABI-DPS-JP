# スキル紐付け・統合表の操作方法と検証結果

## 操作
「スキル」画面の表で、内部名／スキル群、使用回数、ヒット数、総ダメージ、最大、平均、最小、割合、通常のみ、クリティカル候補、強打候補、連打候補を同じ行に表示します。判定欄は回数／その行のヒット数に対する割合です。列見出しを押すと並べ替え、同じ見出しを再度押すと昇順・降順が切り替わります。初期値は総ダメージ降順です。追加攻撃は引き続き未解析です。

上部の全体判定統計と、下部のスキル別表は同じ表示区間です。「現在戦闘／記録全体」で範囲を切り替えます。使用回数もその表示区間のスキル通知数に合わせました。多段・継続攻撃があるため、使用回数とヒット数は一致しません。スキル群の使用回数は候補名の使用通知の合計であり、個別発動との一対一対応ではありません。

## 紐付け条件（実測仮説）
受信方向のTCP接続ごとのJP9パーサー内で、0x5243の直後のフレームが35バイトの0x4FF7であり、攻撃者・対象の16バイトと、5243[32:40]／4FF7[24:32]が一致した場合に限り、4FF7[16:20]を識別子候補として採用します。違うフレームが挟まれば結合しません。

0x1D4F8のUTF-16LEスキル名の後ろが厳密に29バイトの場合だけ、末尾[17:25]を対象ID候補、[25:29]を識別子候補として取得します。対象ID候補は記録しますが、範囲・設置攻撃の対象を根拠なく制限する用途には使いません。

スキル辞書は接続内・攻撃者別です。固定ID辞書を持ち越しません。使用名が一意ならそのスキル、複数なら識別子と候補スキル群に分類します。識別子を取得できてもスキル通知がなければ未特定です。後から同じ識別子の別スキル名が判明した場合、取得セッション内のイベントもスキル群へ再分類します。個別発動IDを特定したという意味ではありません。時刻だけでの割り当てはしません。

分類は既存の1ダメージイベントへの補助情報付与です。4FF7を別ダメージとして加算しません。フレーム待ちのためダメージ集計自体を遅延せず、関連通知到着時に分類を更新します。送受信・別接続の混同はしません。TCP再送除外、HP解析、判定候補ビットの計算は変更していません。

## 検証結果
ローカルで見つかった実通信17本を再生しました。提示文の6本と同一集合と確認したものではありません。以下の分母は既存の入力検査を通過して集計ログへ入ったイベントです。生の全通知件数とは区別してください。

- ダメージイベント：3,025件
- 関連通知との厳密結合：2,965件（98.0%）
- 一意のスキル名：843件
- 複数候補のスキル群：964件
- 名前まで分類できた合計：1,807件（59.7%）
- 未特定：1,218件（40.3%）。うち結合不能60件、結合できても辞書にスキル名がないもの1,158件。

全17本で、分類前後の戦闘別総ダメージ、時間、プレイヤー別ダメージ・DPS・ヒット数が完全一致する回帰テストを通しました。スキル行のダメージ合計も戦闘総ダメージと一致します。入力検査・対象設定で集計対象がない記録では、両方とも0となります。

例：141755の記録では365イベント、結合365、一意219、群91、未特定55。548446の表示区間の累計273,425・DPS2,515は従来と同じです。

949ダメージの構造テスト、別接続の辞書分離、識別子の曖昧化、攻撃者・対象・照合フィールド不一致の拒否、非隣接の拒否、TCP分割、並べ替え、既存の再送処理を検証しました。参考ZIPは現在の添付では確認できず、949テストは提示仕様から構成したテストデータです。参考コードを実キャプチャ由来のまま取り込んだという意味ではありません。

自動テスト91件成功・9件スキップ。Windowsビルド、保存済み通信での画面描画を確認しました。新版の実ゲームでの表示確認は未実施です。

## 残る問題
識別子とスキル名が複数対応するケースを個別スキルへ分解する根拠はありません。捕捉開始前のスキル通知、未対応のイベント形式は未特定として残ります。正式なプロトコル仕様ではなく実測仮説です。クリティカル等も候補表示を維持します。今回、個別発動IDや追加のメッセージIDの解読は行っていません。

配布ZIPにPCAPNGや生ペイロードは含みません。
