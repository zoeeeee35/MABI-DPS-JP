# 制約・実行環境・技術障害の再評価（2026-10-25）

## 質問への回答

1. TCP16000が暗号化されていると確認できているか → いいえ。前回のA/BではTCP16000のTLS形式判定は0。TLSでないことは無暗号の証拠でもない。暗号方式、暗号化フラグ、正当に利用できる鍵・nonce・認証タグ等も未確認。現在の証拠から「暗号化が原因」と結論してはいけない。
2. 圧縮、フレーム変更、旧パーサー非互換の可能性 → いずれもある。現在の旧パーサーは開始シグネチャがなければブロック読取もBrotli展開も行わない。従って「Brotli展開が失敗した」という観測ではない。
3. 指示により避けた処理 → 下記A。通信解析全般を止めたわけではないが、TLSらしさを検出すると旧パーサーを打ち切る実装判断は調査範囲を狭めていた。
4. Codexの環境等でできない処理 → 下記B。一般的な受動キャプチャ、構造解析、公開ライブラリーによる展開、正当に提供された鍵での通常の復号を一律に禁じる制限を今回の原因とする証拠はない。
5. 制約を除いた技術上の未解決事項 → 下記C。制約を除いてもフレーム形式や鍵が自動的に判明するわけではない。

## A：指示による自主的な制限

- 以前の指示に従い、暗号化の突破を目的とする試行はしていない。既知の暗号方式と正当な鍵を受け取った上で実装する依頼が拒否された事実はない。そもそも方式・鍵が未特定。
- 実通信のペイロード/PCAPをファイル保存していない。以前の「内容保存は明示許可後」の条件は継続。外部送信もしていない。これにより後から過去通信を再解析することはできないが、現在のメモリ内解析は可能。
- wireDecoder.feed のTLSらしい先頭5バイト判定で後続の旧形式解析を停止。これは保守的な実装判断。今回、その分岐の前で独立に診断するstructureProbeを追加し、後続の旧マーカーもカウントできるようにした。暗号解読ではない。
- 今後は公開仕様・正当な鍵/データがある通常の復号も技術評価対象。未特定の方式を推測して成功扱いにはしない。
- 既存の許可された取得経路がない、という理由で現在の受動TCP取得を停止してはいない。

## B：実行環境・安全上の制限

- サンドボックスのシェルで物理アダプター一覧や所有PIDテーブルに制限があった。一方、通常起動したWindows EXEのNpcapと所有PID照合でゲーム通信の取得を実証済み。アプリへ権限不足があると断定しない。
- ネットワークアクセスや作業範囲外ファイルへの書き込みには環境上の権限制限がある。今回は取得済み依存のvendorと作業領域内でビルドできる。
- Windows GUI自動操作は状態を確認して行う必要があり、利用者の停止操作を受ければ停止する。ゲーム操作は利用者が手動実施。
- ゲーム改ざん、アンチチート停止/回避、認証情報/秘密鍵の不正取得は行わない。利用者の最新指示も同じ条件。
- 本調査で圧縮展開や適法に提供された鍵の通常の使用がツール側から拒否された事実はない。安全機構が解析を止めた、という説明は根拠がない。

## C：未解決の技術的問題

- ゲーム所有のTCP16000は送受信ペイロードを取得でき、通常攻撃測定で送信データありパケットが増えた。ただし実ダメージの受信経路と未確定。
- TCP順序復元/再送除去とアプリケーションのフレーム境界復元は別。観測バイトと復元バイトの一致は後者の証明ではない。途中からの取得では先行データ/初期状態も不明。
- 長さの位置、エンディアン、ヘッダー長、マジック、複数フレーム連結、分割の仕様が不明。
- 圧縮がフレーム全体かブロック内部か、Brotliか別方式か、辞書が必要か不明。
- 暗号化の有無が不明。暗号であれば方式と正当に利用可能な鍵、IV/nonce、タグ、レコード連番等を確認する必要がある。エントロピーだけでは暗号と断定できない。
- 戦闘レコードの種類/ID、数値表現、攻撃者/対象/スキルの対応が不明。730の偶然一致は証拠にしない。複数の画面数値と攻撃時刻による照合が必要。

## 今回実装した診断

capture_structure.go のstructureProbeをCapturePipeline.collectでwireDecoderより前に実行する。全ての識別済みゲームTCP接続・両方向に適用し、16000固定にしない。

- 連続TCP出力チャンクのサイズ分布（フレーム分布とは呼ばない）。
- 先頭16位置が初回チャンクと一致した回数。実バイト/ハッシュ/名前は出力しない。固定ヘッダーの証明ではない。
- 長さフィールドoffset0/2/4、uint16/32、LE/BE、全長/本文長の24仮説。最大候補長16KiB。完了候補数、連続候補数、候補バイト数、長さ分布、不正長、待機量を出力。
- 仮説は貪欲な追跡のため途中開始で誤った長さに停滞し得る。未対応位置/可変長整数/16KiB超などは候補にならない。候補0でもフレームなしとは言わない。複数条件の独立窓・再測定で確かめる。
- 1つの入力内の複数候補、および複数入力に分割された候補を追跡。3つの独立した合成データで分割方法によらず正しい既知仮説が12フレームを追跡するテストを追加。実ゲームの仮説確定とは別。
- gzip/zstdの既知マジック出現数、旧開始/終了のTLS判定前の出現数。出現だけで形式成立とはしない。
- バイトエントロピーを数値のみ出力。高いことを暗号の証明としない。Brotliには一般的な固定マジックを前提にしない。
- A/B/Cの開始時に構造診断をリセットし、独立の窓にする。TCP順序復元と既存戦闘解析はリセットしない。候補をダメージとしてDPSへ渡さない。

保存するのは統計・モデル名・カウンターのみ。パケット内容は一時メモリ内だけ、個人情報や鍵の抽出/保存/外部送信はなし。安全な既知方式での復号プラグインを必要もなく実装してはいない（方式・鍵・レコード形式がないため）。
